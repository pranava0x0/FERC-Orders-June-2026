# review-ship — review the diff, fix, document, then ship (FERC large-load microsite)

The end-of-work ritual for this repo: an honest code review of what changed, fix what's real,
fold the durable lessons back into the docs, then commit / push / PR / merge. It is the counterpart
to the feature work — run it once a slice (e.g. the P0 items) is built and verified.

**Static, dependency-free site.** `docs/js/app.js` renders `window.FERC_DATA` (`data.js`) and
`window.FERC_COMMENTS` (`comments-data.js`, generated by `tools/build-comments-page-data.mjs`).
All HTML is built as strings with `esc()` on every interpolation — that is the XSS model; do **not**
flag `innerHTML`+`esc` as a vuln. Tests are `node --test tests/*.test.mjs` (no deps). Assets are
cache-busted by `ASSET_VER` in `app.js` + the `?v=` tokens in `index.html`.

## 1 — Scope the diff

- `git rev-list --left-right --count origin/main...HEAD` and `git log --oneline origin/main..HEAD` —
  know what's under review and whether the branch already carries plan/doc commits.
- Review the **code** diff, not the generated output: `git diff origin/main..HEAD -- docs/js/app.js
  docs/js/data.js docs/js/comments-route.js tools/*.mjs docs/css/styles.css docs/index.html tests/`.
  Skip `docs/js/comments-data.js` and `docs/data/comments/**` (generated — the build tool is the source
  of truth) and `*.md` plan docs (reviewed separately).

## 2 — Review for real bugs (recall-biased), scaled to risk

Read every hunk **and its enclosing function** (bugs in untouched lines of a touched function are in
scope). Hunt the failure modes that actually bite this codebase:

- **Scope**: a helper referenced out of scope (e.g. `CM` is a `renderComments` local — `wireComments`
  must bind its own `var CM = window.FERC_COMMENTS`). A `ReferenceError` in synchronous init silently
  aborts the rest of the wiring, and the preview console may show nothing — see LEARNINGS.md.
- **Router / hash state**: `goTab` / `applyCommentsRoute` / `showSub` applying the wrong branch,
  clobbering the hash, or leaving the URL out of step with the visible filter/sub-tab.
- **Delegated click handlers**: mis-targeting (`closest`), stale `NodeList` after an `innerHTML`
  re-render, double-binding.
- **Filters**: AND-token predicates over `data-*`, falsy-zero, empty optional fields (a comment with no
  `bins`/`pr`/`rg`).
- **Dates**: `new Date("YYYY-MM-DDT00:00:00")` (local) vs today (`new Date()` + `setHours(0,0,0,0)`) —
  keep both local; ties on "next"; all-past.
- **Deleted guards**: for every removed line, find where its invariant is re-established.
- **Blast radius past the diff** (2026-08-23, the two worst bugs of that session): when a hunk changes
  what a shared helper *means*, grep every READER of its output, not just its callers. `procStatus()`
  became reset-aware and two untouched functions one call away kept reading `.s.date` off the result —
  the masthead announced a date six days in the past on every tab, with a fully green suite. Untouched
  lines inside the blast radius are in scope; say so to any reviewer agent.
- **Silent success in tooling** (same session, 4 instances in one PR): any branch treating "nothing to
  do" as "done". A `--check` that finds no inputs and exits 0; a flag with a missing operand falling
  through to a normal run; `parseInt(undefined)` → `NaN` → an empty slice; a `catch` that swallows on
  the assumption an error was already recorded. Grep new CLI code for every early return and ask what it
  prints and what it exits.
- **Hardcoded values in display copy** where the rest of the surface is data-driven. One typed date
  outlived the fact it described and kept asserting it above a table that had already been corrected.
  If a page derives every other instance of a value, the literal one is the one that rots.
- **CLAUDE.md conventions**: no em-dashes / "X, not Y" / range dashes in *displayed* copy; ≥44px touch
  targets under `@media (pointer: coarse)`; `[hidden]{display:none}` alongside any `display:` rule on a
  `hidden`-toggled element; derived values labeled derived; never manufacture certainty.

Scale the effort to the risk: for a well-tested diff of your own code, a careful self-review plus **one**
independent adversarial reviewer agent (`general-purpose`, given the code diff) is enough; reserve a
larger fan-out for high-stakes or unfamiliar changes. Dedup, then keep only findings you can substantiate
by quoting the offending line.

## 3 — Fix, then re-verify

- Fix the confirmed findings. Prefer deepening the mechanism over special-casing (altitude).
- `node --test tests/*.test.mjs` — all green. Add a regression test for any bug fixed (the bug is the
  test case). Regenerate + re-run if the fix touched the build tool
  (`node tools/build-comments-page-data.mjs`); generated output commits **with** its generator.
- If the change is observable in the browser, **bump `ASSET_VER` + the `?v=` tokens** and verify with the
  preview MCP: set an explicit `preview_resize({width,height})` first (the viewport can collapse to
  `innerWidth: 0` and blank screenshots / inflate layout), then drive the affected flow with
  `preview_eval` / `preview_inspect` (width-independent, reliable). Check console at all levels.

## 4 — Document the learnings

- **`LEARNINGS.md`** — durable, reusable lessons that cost real time here and will recur (a scope bug that
  aborted init, a preview-loop gotcha, a data-honesty call). Terse, specific, one hook per bullet.
- **`issues.md`** — every bug found + fixed this session: `date · area · description · root cause
  (code/test/data/source) · status`. Move to the Fixed section with the fix + verification.
- **`backlog.md`** — anything deferred with its rationale (e.g. windowing below the DOM-budget threshold;
  a per-RTO filing matrix that needs eLibrary polling). Never let a deferral read as "not needed."
- Promote a genuinely universal lesson to the base `CLAUDE.md` only if it isn't project-specific.

## 5 — Commit, push, PR

- Commit review fixes + doc updates in focused commits, plain-voice messages explaining *what* and *why*
  (no AI co-author / "Generated with" footers — repo rule).
- `git fetch` and integrate onto the latest `origin/main` before pushing to a shared branch; push the
  branch.
- Ensure a PR to `main` exists (`gh pr list --head <branch>`; `gh pr create` if not) with a body that
  summarizes the slice, links the plan, and notes verification + deferrals.
- Address any bot / reviewer comments (e.g. Codex), pushing fixups.

## 6 — Merge only on explicit approval

Merging to `main` is outward-facing. Merge **only when the user has explicitly said so** (in this repo's
history they say "merge" / "commit push merge"). If they only asked to "review and ship" without naming
merge, stop after the PR and report the URL for their review. When merging, confirm CI/checks are green,
`gh pr merge`, then report the merged SHA and clean up the branch if appropriate.

## Report

End with a one-line status: findings (confirmed/fixed vs dropped), tests (`✓ N`), what shipped, the PR
URL, and whether it was merged or is awaiting review.
